# Microbenchmarks

The microbenchmark jobs run the PHP tracer's, AppSec's and the profiler's
benchmark suites inside the Datadog
[Benchmarking Platform](https://datadoghq.atlassian.net/wiki/spaces/APMINT/pages/2419261562/Benchmarking+Platform)
and compare the results against a baseline to detect performance regressions
on every PR.

This directory holds everything the microbenchmark jobs need:

- **`container/`**: Dockerfile for the `MICROBENCHMARKS_CI_IMAGE` CI image,
  built in-repo via the
  [`build-ci-images.template.yml`](https://github.com/DataDog/benchmarking-platform-tools/blob/main/images/templates/gitlab/build-ci-images.template.yml)
  include (see [How to rebuild the CI Docker image](#how-to-rebuild-the-ci-docker-image)).
- **`steps/`**: PHP checkout, BOLT preparation and execution scripts, plus
  the Datadog agent configuration script.
- **`bp-runner.yml`**: [bp-runner](https://github.com/DataDog/benchmarking-platform-tools/tree/main/bp-runner)
  experiment definition: captures hardware/software info, starts a local
  Datadog agent, does the one-time setup (ini appends, mysql and redis start,
  sysctl), clones the candidate and the baseline and runs `benchmark/runall.sh`
  on pinned CPUs, converts the results per framework (PHPBench, tea's Google
  Benchmark, Sirun), and uploads the reports to S3.
- **`bp-runner.pr-comment.yml`**: posts the comparison on the PR and uploads
  the converted results to the Benchmarking Platform API (run by the separate
  `benchmarks-pr-comment` job; `bp-runner.pr-comment-appsec.yml` and
  `bp-runner.pr-comment-profiler.yml` are the same flow with the AppSec and
  profiler comment headers, run by `benchmarks-pr-comment-appsec` and
  `benchmarks-pr-comment-profiler`).
- **`bp-runner.fail-on-regression.yml`**: gate config used by
  `check-big-regressions` to fail the pipeline on regressions above its
  threshold (10%).

The jobs themselves (`benchmarks-tracer`, `benchmarks-appsec`,
`benchmarks-profiler`, `benchmarks-pr-comment`, `benchmarks-pr-comment-appsec`,
`benchmarks-pr-comment-profiler`, `check-big-regressions`) are defined in
[`.gitlab/benchmarks.yml`](../benchmarks.yml), which runs as a child pipeline
of `package-trigger` (the stage list it validates against is generated by
`.gitlab/generate-package.php`).

Execution flow on each PR:

1. Each benchmark job sets `SCENARIO` (`tracer`, `appsec` or `profiler`) and
   runs `bp-runner .gitlab/benchmarks/bp-runner.yml`: hardware/software info
   capture, Datadog agent, one-time setup, then the candidate and baseline
   runs. The PHP step resolves the PR's merge-target branch with
   `github-find-merge-into-branch` (or uses `BASELINE_BRANCH` when set), then
   takes its merge base with the exact candidate commit.
   Both revisions are compiled and aligned before either is measured.
2. Each run's `benchmark/` suite results are saved as
   `reports/$BASELINE_OR_CANDIDATE-<name>.<ext>` artifacts; only the AppSec job
   also uploads the logs, tarred as `candidate.tar.gz`/`baseline.tar.gz`.
3. The config's analyze steps convert the results per framework (PHPBench,
  GoogleBenchmark for tea, Sirun) and the S3 teardown archives the reports;
   `benchmarks-pr-comment*` jobs run their `bp-runner.pr-comment*.yml` to
   push the converted results to the Benchmarking Platform API so they land on
   the project's trend series.
4. `check-big-regressions` gates the pipeline on regressions above the
   threshold of 10% in `bp-runner.fail-on-regression.yml`, and
   `benchmarks-pr-comment*` comments the comparison on the PR.

## Binary layout processing

All three scenarios measure the combined `ddtrace.so`. For comparisons,
`llvm-bolt-align` rewrites both the baseline and candidate after linking,
placing their common functions at matching offsets. It does not replace
the linker and requires no profile. Both builds retain relocations with
`-Wl,--emit-relocs` and disable GCC's hot/cold block partitioning with
`-fno-reorder-blocks-and-partition`.

Set the CI variable `BOLT_MODE` to choose the processing step:

| Value | Processing after linking |
| --- | --- |
| Empty (default) | `align` when a baseline exists; `plain` for a candidate-only run. |
| `align` | Pairwise rewrite with `llvm-bolt-align`; requires a baseline. |
| `plain` | Independently rewrite each module with `llvm-bolt`, without a profile. |
| `off` | Run the normally linked modules without BOLT processing. |

Explicit alignment fails when no baseline can be found. A failed baseline
lookup also fails the job. The candidate-only default applies when the
lookup succeeds and returns no target branch, as on master runs.
Both source revisions must contain the combined-extension harness from
[#4520](https://github.com/DataDog/dd-trace-php/pull/4520); older harnesses
are rejected because they rebuild separate modules.

The PHP image copies a static LLVM 23.1.6 build with
[`llvm-bolt-align`](https://github.com/llvm/llvm-project/pull/210634)
from a digest-pinned tool image. `llvm-bolt` and `llvm-bolt-align` use the
same executable, selecting their operation by the invocation name.
The LLVM 16 packages in the PHP image serve the existing compiler/LTO
toolchain; BOLT runs after linking.

`DD_TRACE_ASSUME_COMPILED=1` prevents the benchmark harness from rebuilding
the rewritten module. The installed and build-directory modules are
checked against the selected BOLT output after each run. Unsatisfied
alignment constraints or unexpected module replacement fail the job.
`reports/bolt-mode.txt` records the processing mode, and `reports/bolt/`
retains the tool's diagnostic logs. Temporary BOLT outputs are removed when
the step exits. Checkouts remain at `/app/candidate` and `/app/baseline` for
the shared analyzer to read their Git metadata; they are not uploaded.

The checkout/build/rewrite/run workflow tests can be run on Linux without
compiling PHP or LLVM:

```bash
uv run .gitlab/benchmarks/tests/test_bolt_workflow.py
```

## How to add a new microbenchmark

Where a benchmark lives depends on the scenario it belongs to:

- **tracer / appsec** (`benchmarks-tracer`, `benchmarks-appsec`): PHPBench
  suites in [`tests/Benchmarks/`](../../tests/Benchmarks/), with
  tracer benchmarks in the default groups, AppSec ones under the
  `frameworks` group (`BENCHMARK_EXTRA="--group=frameworks"`).
- **tracer, tea** (`benchmarks-tracer`): C++ Google Benchmark suite in
  [`tea/benchmarks/`](../../tea/benchmarks/).
- **profiler** (`benchmarks-profiler`): sirun suites in
  [`profiling/benches/`](../../profiling/benches/), run through
  [`benchmark/runall.sh`](../../benchmark/runall.sh) with a natively compiled
  profiler.

1. Add the benchmark in the matching location, following the existing
   patterns there.
2. Run it locally the same way the job does (see
   [How to run the suite locally](#how-to-run-the-suite-locally)).
3. Push the branch and let the benchmark job run: new benchmarks are picked
   up automatically: the scenarios are discovered from the suites' own
   result files, not from a list. On the first run the baseline may not
   contain the new benchmark, so it appears as candidate-only in the
   comparison.

## How to update an existing microbenchmark

Edit the benchmark where it lives (see above). Keep in mind that the baseline
run executes the *baseline checkout's* copy of the suite, so a benchmark that
was renamed or removed on the candidate is still measured on the baseline;
expect a one-run mismatch on renames. If the benchmark becomes unstable while
you iterate, see
[How to mark a benchmark as known flaky](#how-to-mark-a-benchmark-as-known-flaky).

Changes to the benchmark CI (this directory, `.gitlab/benchmarks.yml`) run
`benchmarks-tracer` like tracer changes do. AppSec and profiler stay manual
unless their sources change: play the benchmark job to exercise a CI change
there; its `benchmarks-pr-comment-*` job follows automatically.

## How to mark a benchmark as known flaky

Add it to `FLAKY_BENCHMARKS_REGEX` in the matching template's `variables` in
[`.gitlab/benchmarks.yml`](../benchmarks.yml): the `.microbenchmarks` template
for the microbenchmark jobs, or the `.macrobenchmarks` template for the
macrobenchmarks. The benchmark
still runs and reports, but doesn't fail performance quality gates
(`check-big-regressions` here, percentage-based; `check-slo-breaches` for the
macrobenchmarks, SLO-based).

- The regex matches anywhere in the scenario name.
    - `SpanBench` quarantines every `SpanBench` scenario.
    - Anchor with `^...$` to target one scenario.

```yaml
FLAKY_BENCHMARKS_REGEX: "SpanBench|^webserver--laravel-realworld--baseline--none--normal_operation$"
```

Open a ticket to fix or remove it. See
[Flaky Benchmarks Monitoring](https://datadoghq.atlassian.net/wiki/spaces/APMINT/pages/7223313012/Flaky+Benchmarks+Monitoring).

## How to rebuild the CI Docker image

The `MICROBENCHMARKS_CI_IMAGE` used by the microbenchmark jobs is built from
`container/Dockerfile` in this directory. Rebuild and repin it whenever you
change anything in that directory (e.g. bumping PHP, adding system packages,
or updating `sirun`).

1. Edit the relevant file(s) under `.gitlab/benchmarks/container/`. Push the
   branch and open a PR.

2. The pipeline includes
   [`build-ci-images.template.yml`](https://github.com/DataDog/benchmarking-platform-tools/blob/main/images/templates/gitlab/build-ci-images.template.yml),
   which defines a manual `build-benchmark-ci-images` job that builds the
   image from `BASE_CI_IMAGE_CONTAINER_DIR` (`.gitlab/benchmarks/container`)
   and pushes it as
   `registry.ddbuild.io/ci/benchmarking-platform:$BASE_CI_IMAGE_SUFFIX`
   (`dd-trace-php-<pipeline id>`, one unique tag per pipeline, so a rebuild
   can't shift what older pipelines pulled).

3. Open the pipeline on
   [gitlab.ddbuild.io/DataDog/dd-trace-php](https://gitlab.ddbuild.io/DataDog/dd-trace-php)
   (the `package-trigger` child pipeline), play the
   `build-benchmark-ci-images` job, wait for it to finish, and copy the
   resulting image tag from its logs.

4. Repin `MICROBENCHMARKS_CI_IMAGE` in `.gitlab/benchmarks.yml` to that tag:

   ```yaml
   # Built here: <paste build-benchmark-ci-images job URL>
   MICROBENCHMARKS_CI_IMAGE: registry.ddbuild.io/ci/benchmarking-platform:dd-trace-php-<NEW_PIPELINE_ID>
   ```

5. Push the update. The microbenchmarks now run against the rebuilt image.
   Verify a green benchmark pipeline before merging.

## How to run the suite locally

The suites themselves live in the tracer repository, so the quick feedback
loop is to run them the way `benchmark/runall.sh` does, without the
Benchmarking Platform wrapper:

- tracer / appsec (PHPBench, see `benchmark/runall.sh`):
  ```bash
  make composer_tests_update          # once, to install benchmark dependencies
  make benchmarks                     # tracer PHPBench scenarios
  make benchmarks_opcache             # the same scenarios under OPCache
  make benchmarks_tea                 # the C++ Google Benchmark suite
  # For the combined-extension AppSec run, use benchmark/runall.sh below.
  ```
- combined-extension suites: from `benchmark/`, run
  `SCENARIO=profiler ./runall.sh` (or `tracer` / `appsec`) with
  `ARTIFACTS_DIR` set to an absolute output directory. The profiler's sirun
  workloads load `tmp/build_combined/modules/ddtrace.so`.

To reproduce a full CI run including the baseline comparison, run the job's
steps from the repository root with the environment the CI job provides
(`SCENARIO`/`BP_SCENARIO`, `ARTIFACTS_DIR`). Also export the analyzer
variables the CI jobs set (`UNCONFIDENCE_THRESHOLD=2.0`, `CI_TYPE=theoretical`,
`MD_REPORT_ONLY_CHANGES=1`); without them the local analysis uses a
significance threshold of 1.0 and prints the unchanged-results table:

```bash
export ARTIFACTS_DIR="$(pwd)/reports"
export UNCONFIDENCE_THRESHOLD=2.0 CI_TYPE=theoretical MD_REPORT_ONLY_CHANGES=1
SCENARIO=tracer BP_SCENARIO=tracer bp-runner .gitlab/benchmarks/bp-runner.yml --debug -t
```

Note that `bp-runner.yml` starts a real Datadog agent (the API key comes from
AWS SSM in CI, set `DD_API_KEY` yourself locally), needs a GitHub token for
the baseline lookup, and pins the benchmark CPUs (34-47 on the 48-core CI
runners), so a faithful local run needs a comparable machine.

## Other benchmark suites (not in this directory)

- `macrobenchmarks` and the `linux-php-*-parallel` jobs: defined in
  `.gitlab/benchmarks.yml` but their steps still live in the
  `php/laravel-realworld` branch of
  [benchmarking-platform](https://github.com/DataDog/benchmarking-platform)
  and in [apm-sdks-benchmarks](https://github.com/DataDog/apm-sdks-benchmarks/tree/main/.gitlab).
- `dsm-throughput`: steps live in the `php/data-streams-monitoring` branch of
  benchmarking-platform.
